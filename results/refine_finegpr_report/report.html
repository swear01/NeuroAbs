NeuroAbs：LLM 選 refinement 單元，以及更細的抽象選單

2026-10-26 · Piccolo ILA property · rIC3 only · DeepSeek V4 Flash · PR #15（A）、#16（B），兩者都未 merge

一句話：更細的選單（拆 property、GPR 逐個選、加法器換成 UF）讓 Piccolo ADDI、LUI、AUIPC、JAL 的 ILA property 第一次被 rIC3 證出來，B0 在 30–60 分鐘內都沒有結論。但證得出來靠的是選單設計：LLM 選得比自動 CEGAR 好很多，卻沒有比一條十行左右的結構規則好。A 實驗裡，LLM 每次 refinement 都退到需要的單元，但最終模型仍沒有結論。

1. 背景

ILA property

每個題目（ADDI、LUI…）都在比較同一條指令的兩個模型：ILA 規格模型和 Piccolo RTL。wrapper 用兩個時間點把它們綁在一起：

  • __START__：ILA 在這一拍執行這條指令。ILA 的暫存器 xj 被 assumption 設成 recorder __auxvarN__recorder。recorder 是一個自由常數，另一條 assumption 要求它等於指令走到 stage 3 時 RTL 的 arr_j。
  • __IEND__：指令在 RTL 裡完成。assertion 要求 ILA 的 pc、load_en、store_en、x0..x31 都等於 RTL 對應的值。

所以原 property 是 35 個 conjunct 的 AND，其中 31 個是在比對 GPR。

抽象單元與等級

等級意思
keep原樣保留
havoc單元裡的記憶體每次被讀，都回傳任意值（每拍各自獨立）；控制邏輯保留
cut整個 instance 的所有輸出，每拍都是任意值

Piccolo 有 4 個單元：csr_regfile（keep/cut）、gpr_regfile_regfile（keep/havoc/cut）、near_mem_dcache、near_mem_icache（keep/cut）。它們都是 over-approximation：抽象模型保留原設計所有的行為，所以在抽象模型上證明成立，原設計也成立。

CEGAR 與名詞

  • 反例（counterexample）：從初始狀態出發、讓 assertion 失敗的一條具體 trace。深度 k = trace 有 k+1 拍（cycle 0..k），assertion 在第 k 拍失敗。
  • 假反例（spurious）：只在抽象模型裡存在、原設計做不到的反例。原因是某個任意值取到了原設計不可能出現的值。
  • CEGAR：從很粗的抽象開始跑 rIC3。拿到反例就把它在抽象模型上重放，看 assertion 失敗那一拍的 cone 裡用到了哪些單元的任意值（choice__<unit>__n），這些單元就是候選。挑一個（或多個）候選往 keep 退一級，再跑一次。
  • COI bits：property 的 cone of influence 裡有多少個 state bit，用來量模型大小。B0（不抽象）= 5,131。
  • B0：完全不抽象、整條 property 直接交給 rIC3。

2.1 標準答案怎麼來的，「每一步都選對」的精確意思

問：你怎麼知道它每一步都對？
答：我們事先另外算了一份標準答案，再拿每一步去對照。這份標準答案是用有界 BMC 做的，不是完整證明。所以「對」的意思比較窄，細節如下。

第一步：每個單元單獨變粗。其他三個單元保持 keep，跑 ric3 … bmc --end 20，限時 900 s（scripts/screen.py）。ADDI 的原始紀錄（piccolo/ADDI/screen.jsonl）：

只改這個單元BMC 到深度 20耗時判斷
gpr havocSAT，深度 115.9 sGPR 必須 keep
icache cutSAT，深度 115.2 sI-cache 必須 keep
csr cut到 20 都沒有反例746 s可以 cut
dcache cutTIMEOUT（ADDI 這題沒跑到 20）905 s沒有結論，暫定可以 cut
csr cut + dcache cut 一起TIMEOUT（ADDI 到深度 18 還沒有反例）902 s沒有結論
  • 「需要」這一邊是可靠的。只把 u 變粗就出現反例，代表 u 這麼粗不夠。其他單元再變粗只會多出行為，這個反例仍然存在。所以任何安全的模型都必須讓 u 比這個等級更細。
  • 「可以 cut」這一邊只是有界的。到深度 20 內沒有反例，不代表沒有更深的反例。12 題中有 10 題「csr cut + dcache cut」到深度 20 都沒有反例；ADDI 和 ADD_Flatten 只跑到 18。PR #14 也用 portfolio 跑過這個模型 3600 s，沒有找到反例，但也沒有證出來。
  • 所以「最小安全模型 4,136 bits」的精確意思是：在這個 4 單元選單裡，深度 20 內沒有已知反例的最粗組合。

第二步：判斷每一步。（scripts/evaluate.py）

  • 需要的一步：退的單元 u 當時比標準答案還粗。LLM 108/108；one 36/59，all 36/60，bmc 36/48。
  • 單獨就能消掉反例的一步：只退 u 的模型，在反例深度內沒有反例。LLM 只有 70/108。原因是 GPR 和 I-cache 兩個都需要，有些反例必須兩個都退才會消失。

所以「每一步都對」的精確說法是：LLM 沒有任何一步浪費在不需要的單元上，而且 36 次都停在上面那個 4,136-bit 的組合。這不代表每一步都是最好的一步。還有一點：12 題需要保留的單元完全一樣，assertion 也直接點名了 GPR（…regfile…arr_j）和指令記憶體（imem_pc），這題對 LLM 很容易。

2.2 「GPR havoc 和 I-cache cut 在深度 11 出現反例」是什麼

這是指：在「只有 GPR 是 havoc、其他保留」的模型上，BMC 找到一條 12 拍（cycle 0–11）的 trace，第 11 拍 __IEND__ 時 assertion 不成立。這條 trace 在真實 Piccolo 上做不到，是假反例。

screen 只記錄了 SAT 和深度，沒有存 witness。不過 CEGAR 跑的時候，在相近的模型上重放過 witness，從那裡可以看出是哪些任意值造成的。以 ADDI LLM 第 1 次 run 的紀錄為例（arms/llm-1/refine-iter*.json）：

模型反例cone 裡的任意值（被驅動的訊號與拍數）怎麼讀
全部 cut（iter 0）9 拍，第 8 拍失敗icache 11 個：near_mem$imem_pc、imem_valid、icache$word64（cycle 5, 6）；csr 10、dcache 12、gpr 4I-cache 被 cut，取到的指令和 PC 可以是任意值，所以 __ILA_SO_pc == imem_pc 那條會失敗。LLM 選 icache（p=0.6）
icache keep，gpr cut（iter 1）12 拍，第 11 拍失敗gpr 5 個：regfile$D_OUT_1、D_OUT_3（cycle 8, 9），arr_16（cycle 11）；csr 14、dcache 5暫存器檔案讀出的值和 arr_16 本身都是任意值，第 11 拍比對 x16 時，RTL 的值和 ILA 的值不同。LLM 選 gpr（p=0.81），退到 havoc

所以「GPR havoc 有深度 11 的反例」的意思就是第三列這種情況：只要暫存器讀出來的值是任意的，RTL 和 ILA 執行同一條 ADDI 就可能得到不同結果，而且最短 12 拍就能走到 __IEND__ 比對。I-cache cut 的反例則是指令和 PC 可以亂給。反例裡 csr、dcache 的任意值都只驅動 reset 握手（RDY_server_reset_*）和 interrupt_pending、nmi_pending，跟比對的值沒有關係。這正是 LLM 能判斷它們不需要的線索。

bmc 策略錯在第一步：全部 cut 時那條深度 8 的反例，退 icache 或退 dcache 都會讓它消失，而 dcache 的模型比較小，所以它選了 dcache。但 dcache 其實不需要。

3. 實驗 B：更細的選單（PR #16）

PR #14 的選單是每個 module instance 選 keep/havoc/cut。在 Piccolo ADDI ILA 上，這個選單的任何組合跑 1 小時都沒有結論。原因是 GPR 檔案必須整個 keep，而 property 要比對全部 31 個 GPR。B 在這個選單上加了三種新選項。

3.1 三種新選項

問：「新選項」是什麼意思？
答：就是下面這三種原本選單沒有的抽象方式。它們都由 src/fine_choice.py 改寫 wrapper，或在 Yosys 加 cut point 產生，而且都是 sound 的。

① 拆 property

原 assertion 是 35 個 conjunct 的 AND。每個子 property 只保留其中幾個 conjunct，而且可以加一個 case，也就是對 ILA 正在執行的那條指令的欄位設條件。

指令在 __START__ 時被鎖存到一個觀察用的暫存器 __split_inst__（它不影響設計行為），子 property 的 assertion 改成 !case || p。

② GPR 逐個選

原本的 GPR 單元換成 32 個選項 gpr0..gpr31，每個各自有三種等級：

  • keep：保留
  • word：暫存器的值保留，但拿掉「ILA 的 xj 等於 RTL 的 arr_j」這條起始 assumption
  • havoc：RTL 的 arr[j] 和 ILA 的 xj 每拍都是任意值，只跟被移除的 GPR 有關的 assumption 也一起拿掉

③ 加法器換成 UF（Ackermann）

把 ILA 的 n110 = n107 + n109 和 RTL ALU 的 rd_val___1__h6550 = rs1_val_bypassed + imm 配成一對，兩邊的結果每拍都變任意值。

在 __START__ 鎖存兩邊的運算元和結果，再加一條 assumption：運算元相同，結果就相同。

這樣 IC3 不必學 carry chain，需要的 lemma 都只是「兩個鎖存下來的 word 相等」。

為什麼 sound

  • cut point 把驅動換成任意值，任意值包含原本的值。
  • 拿掉 assumption 只會讓限制變少。
  • UF：在真實 trace 裡，任意結果可以取真實值，那條 assumption 就自然成立。
  • 拆 property：下一節證明子 property 涵蓋了所有情況。

所以所有子 property 都在抽象模型上被證出來，原 property 就在原設計上成立。

3.2 ADDI 的 1024 個子 property 怎麼算

子 property比對哪個 conjunctcase個數
mempc、load_en、store_en、x0所有指令1
xk.frame，k = 1..31xkrd != k：這條指令不寫 xk，xk 應該保持不變31
xk.rs1=r，k = 1..31，r = 0..31xkrd == k && rs1 == r：這條指令把 x[r] + imm 寫進 xk31 × 32 = 992
合計1 + 31 + 992 = 1,024

為什麼這樣拆不會漏：對每個 k，rd != k 加上 32 個 rd == k && rs1 == r 涵蓋了所有指令；而 35 個 conjunct 每一個都出現在某個子 property 裡。所以全部子 property 成立，原 property 就成立（ila_split 有對應的 test）。

為什麼要依 rs1 拆：寫入的情況需要讀 x[r] 的值。依 rs1 拆開後，每個子 property 只需要保留 2 個 GPR（rs1 和 rd），其他 30 個都可以 havoc。不拆就要保留全部 GPR，結果會 TIMEOUT（見 3.4）。

LUI、AUIPC、JAL 沒有暫存器運算元，寫入的情況不必依 rs1 拆：1 + 31 + 31 = 63 個。

3.3 全部拆開，會不會 state 爆炸？

問：全部拆開不會 state 爆炸嗎？
答：每個子 property 的模型不會變大，反而小很多。會增加的是「要跑幾次」，而且是線性增加。

  • 模型大小：拆 property 只多了觀察用的 __split_inst__（32 bit），UF 多了幾個鎖存。因為每個子 property 只保留 1–2 個 GPR，其他 GPR 和 csr、dcache、icache 都 cut，COI 反而大幅縮小。ADDI sample 的最終 COI 中位數是 1,012 bits，LUI 是 788 bits；B0 是 5,131 bits。
  • 每次 check 的難度：每個子 property 是一次獨立的 rIC3 check，中位數 31–46 s，最慢 81 s。
  • 總次數：ADDI 要 1,024 次 check，加起來是 11.0 個「2-CPU 小時」。同時跑 4 個，實際 2 小時 52 分。B0 用 16 核跑 1 小時都沒有結論。
  • 真正會爆炸的是 R-type。ADD、SUB 這類指令要同時依 rs1 和 rs2 拆，寫入的情況變成 31 × 32 × 32 個，總共 1 + 31 + 31,744 = 31,776 個子 property（README 寫成約 32,768）。這是次數爆炸，不是 state 爆炸，但也已經不實用了。可能的方向是利用暫存器編號的對稱性只跑代表性的 case，或換一種拆法。這些都還沒有試。

3.5 誰來選：auto、LLM、結構規則

問：「LLM 只贏過自動 CEGAR，贏不過一條幾行的手寫規則」是什麼意思？
答：每個子 property 都要決定 36 個選項（3 個單元、32 個 GPR、1 個 UF）的等級。我們比了三種決定方式，下面是結果。

方式怎麼決定之後
auto從最粗開始：單元全部 cut、GPR 全部 havoc、UF 開啟CEGAR，每次退反例裡任意值最多的那個選項
DeepSeek每個子 property 呼叫一次。輸入 case 說明、36 個選項與等級、assertion 和 case；輸出 JSON同 auto
結構規則 Ssrc/fine_choice.py:247 的 structural()，不用 LLM（下面是它的虛擬碼）同 auto
def structural(sub, units, ufs):
    named   = 這個子 property 比對到的 GPR       # 例如 x5
    sources = case 裡寫的 rs1 / rs2 == r        # 例如 x6
    rd      = case 裡寫的 rd == k
    spec = coarsest(...)                        # 單元全部 cut、GPR 全部移除、UF 全開
    spec["keep_gprs"] = (named - rd) | sources   # 保留被比對的（非 rd）和來源暫存器
    spec["word_gprs"] = (named & rd) - sources   # 被寫入的 rd 設成 word
    return spec

例如 x5.rs1=6：保留 x6，x5 設成 word，其他 30 個 GPR 移除，csr、dcache、icache 全部 cut，加法器換成 UF。

    • frame 的情況，它每次都先把 icache、csr、dcache 退回來，最後才退被比對的 GPR，所以很慢。
    • 寫入的情況，單元都退回來之後，反例裡任意值最多的變成 UF，它就把 UF 也退回成真的加法器，結果 TIMEOUT。TIMEOUT 不會產生反例，CEGAR 沒辦法再修正。32 個寫入的情況，它只證出 2 個，都是 rs1 = 0。
  • DeepSeek 為什麼贏過 auto：它一開始就選了 csr、dcache、icache 全部 cut，保留被比對的 GPR 和 rs1，大多只需要 0–1 次 refinement。有 55/64 跟 S 選得一模一樣。
  • DeepSeek 的失敗：
    • 4 個寫入的情況保留了加法器（UF 設成 keep），全部 TIMEOUT，沒有反例可以修正。
    • 在 LUI 和 JAL 各有 1 個 frame 的情況，它把被比對的 GPR 設成 word。這會拿掉起始那條相等的 assumption，所以反例在抽象模型上是真的。但 CEGAR 會先退回反例裡有任意值的單元，refine 10 次就到上限，還沒輪到把那個 GPR 退回 keep。
  • 為什麼贏不過 S：選單細到這個程度後，答案直接寫在子 property 的名字裡。x5.rs1=6 就是保留 x6、比對 x5。S 把這件事照字面寫成十行左右的程式。LLM 能做到的最好也就是選出同樣的答案，而它偶爾會選錯。
  • 不公平之處：S 是子 session 看過 wrapper 結構之後寫的，本身帶了人的領域知識。所以這個比較說明的是：這組題目不需要 LLM 的判斷。它不能證明 LLM 在別的題目上沒有用。

4. 結論、限制、下一步

  1. 選單的設計是證得出來的關鍵。拆 property、GPR 逐個選、UF，三者一起用，才讓 ADDI、LUI、AUIPC、JAL 證得出來，缺一個都不行。
  2. 兩個決策點交給 LLM，都比現在的自動作法好。A：每一步都退到需要的單元，只有它停在 4,136 bits。B：60/64 對 34/64，時間只要 auto 的 1/6。
  3. 但都贏不過、或只是追平簡單的規則。這兩組題目的答案都寫在 property 的文字裡：A 的 assertion 點名了 GPR 和 imem，B 的子 property 名字點名了要保留的暫存器。所以目前不能說「LLM 讓驗證變快」，只能說「LLM 比 auto CEGAR 好」。

限制

  • 只有一個設計（Piccolo）。A 的 12 題需要保留的單元完全相同。
  • A 的標準答案只做到 BMC 深度 20，有兩題只到 18。A 的最終模型都沒有結論。
  • B 的時間混用了 P-core 和 E-core，機器上同時還有另一個 session，只有同一組內的時間可以互相比較。
  • B 沒做的：Flute、ANDI 和 SLTI 的完整證明（SLTI 沒有可以配對的運算子）、R-type（約 3.2 萬個子 property）。
  • B 的 refinement 有一個限制：只要還有單元在反例裡有任意值，它就不會把 word 的 GPR 退回 keep。DeepSeek 的 2 個失敗就是卡在這裡。

下一步建議：找「需要保留的東西沒有寫在 property 文字裡」的題目，LLM 的判斷才有機會勝過規則。例如 Flute 的 R-type、需要 branch predictor 或 bypass 的 property，或其他 SoC。R-type 也需要比 rs1 × rs2 更省的拆法。
