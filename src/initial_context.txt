Abstraction in formal verification is correctly described as a technique for simplifying verification by hiding unnecessary details, where properties proven on the abstract model transfer to the concrete model. The key requirement is that the abstraction must be an over-approximation of the original system, meaning that every behavior possible in the original system must be possible in the abstract system (though the abstract system may allow additional behaviors). This relationship is formally verified by checking that !(original_formula -> new_formula) is unsatisfiable. When this holds, any safety properties proven on the abstract system will also hold for the original system. Here is one brief example on the abstraction

Original:

wire[7:0] ex_alu_result =  id_ex_op == OP_ADD ? id_ex_operand1 + id_ex_operand2 :                             id_ex_op == OP_SET ? id_ex_operand1 :

id_ex_op == OP_NAND ? ~(id_ex_operand1 & id_ex_operand2) :                                                 8'bxxxxxxxx; // OP_NOP

After abstraction:

wire[7:0] ex_alu_result = id_ex_op == `OP_ADD ? id_ex_operand1 + id_ex_operand2 : 'bx;

This is a valid abstraction because any value produced by the original ALU for non-ADD operations will be included in the set of possible values represented by 'x' in the abstract version. Therefore, original_formula -> new_formula always holds true.
